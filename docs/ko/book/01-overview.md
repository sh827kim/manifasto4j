**01. Manifesto 한눈에 보기 (Java 관점)**
Manifesto는 **“결정적 계산(Brain)”과 “현실 실행(Hands)”을 분리**하는 아키텍처입니다. 같은 입력이면 같은 결과가 나오고, 누가 무엇을 왜 바꿨는지가 남도록 설계합니다.

**이 장에서 다루는 것**
1. Manifesto가 풀려는 문제
2. 핵심 원칙(결정성·책임성·분리)
3. 큰 그림 데이터 흐름
4. Java 개발자가 이해하면 좋은 포인트

**Manifesto가 풀려는 문제**
- 복잡한 도메인 로직을 **재현 가능한 계산**으로 만들기
- AI/자동화가 개입해도 “왜 이런 결과가 나왔는지” **설명 가능**하게 만들기
- 승인/거절의 책임을 명확히 남기기

**핵심 원칙**
- 결정성: 동일 입력은 동일 출력
- 책임성: 모든 변화는 Actor + Authority + Intent로 추적
- 분리된 책임: Core는 계산, Host는 실행, World는 거버넌스
- 설명가능성: 값의 근거가 Trace로 남음

**큰 그림 흐름**
1. 사용자가 이벤트를 발생시키면 Bridge가 Intent로 변환합니다.
2. World가 승인 여부를 판단합니다.
3. Host가 Core에 계산을 요청합니다.
4. Core가 Patch와 Effect 요구사항을 반환합니다.
5. Host가 Effect를 실행하고 Snapshot을 갱신합니다.

**Java 개발자에게 중요한 감각**
- **Core는 순수 함수 영역**입니다.
  - 예외 던지기, DB 호출, 외부 API 호출 금지
  - `Date.now()` 같은 벽시계 접근도 금지
- **Host는 실행기**입니다.
  - 실제 I/O, 네트워크, DB를 담당
  - Core의 계산 결과(Patch/Effect)를 “그대로 실행”만 합니다
- **World는 거버넌스**입니다.
  - 승인/거절 정책, 책임 추적, 감사 로그
- **Snapshot은 진실의 유일한 소스**입니다.
  - Core는 Snapshot 밖의 정보를 보지 않습니다

**짧은 예시 (개념)**
아래는 “카운트를 1 올려라”라는 의도를 계산하는 간단한 Flow입니다.

```mel
domain Counter {
  state { count: number = 0 }

  action increment() {
    when true {
      patch count = add(count, 1)
    }
  }
}
```

**이 장의 요점 정리**
- Manifesto는 “계산”과 “실행”을 분리합니다.
- 실행 과정은 Snapshot으로만 이어집니다.
- 거버넌스는 World가 담당합니다.

**현재 Java 포팅 관점 참고 (2026-02-03 기준)**  
- Core는 대부분 정합하지만, 내부에서 시스템 시간을 직접 쓰는 부분이 남아 결정성 이슈가 있습니다.  
- Host/App/Bridge는 최소 실행 레이어만 구현되어 있어 “World 기반 승인 흐름”은 추가 설계가 필요합니다.

**체크포인트 질문**
1. Core가 절대 하면 안 되는 일은 무엇인가요.
2. Host가 해서는 안 되는 일은 무엇인가요.
3. World가 기록하는 핵심 정보는 무엇인가요.
